## B. Waiting capital preview

`previewCapital` is client-local: enabled, tile ID, side, rotation, anchor and a position lock. Waiting and active players use the existing map-ghost renderer. Both faces remain readable; map movement, flip, rotate and camera controls remain available. A map click holds the attempted position; Move releases it.

The two-browser test instruments both action submission and presence. Moving, rotating, flipping and zooming a waiting ghost emits zero such packets and leaves the authoritative state byte-identical. Its outline uses the local player's colour. The other client has no preview. There are no blanket legal-anchor hints.

Only `setup.order[setup.turnIndex]` can commit. A forged waiting-player transaction is rejected. When the preceding player occupies the planned location, the waiting ghost keeps its anchor and becomes invalid; it neither snaps nor commits automatically. The new active player must move it and explicitly confirm.

An independent rule fixture proves that touching another capital is permitted, but its spaces do not count toward the required four core/fort contacts. Fort contacts do count.

Real pointer hit-testing also found the camera controls had no positioning CSS: they fell below the canvas, and the event dial could cover them. They now occupy an explicit top-left column on the map, with space reserved beside the wonder strip so that neither covers the other. The waiting-player test physically clicks Fit and zoom; it does not click through the dial using DOM shortcuts.

## C. Astronomy inspection count

The printed card says **“Look at up to 2 map tiles”**. Zero, one and two therefore remain legal. Inspect 2 Tiles is primary, with Inspect Fewer exposing Inspect 1 and Skip Inspection. A one-tile stack offers Inspect 1 as primary, never an impossible two.

## D. Astronomy origin

The shared predicate requires an active hex with exactly the actual capital's nonempty tile ID, plus a missing/inactive map neighbour. Water is not excluded: the printed origin rule has no land qualifier.

The old helper's `hex.tileId === capital.tileId` accidentally matched every other null-ID space when the capital lacked a tile ID. It now fails closed. The UI previously combined cached highlighted spaces with choices; it now displays the exact central origin set and rechecks it on clicks. The reducer independently rejects rival-capital, core, fortress, unrelated edge and own-capital interior origins, including forged selected-origin payloads.

These are confirmed weaknesses, not proof that every location in the user's unsaved playtest had a missing ID. No reproduction save was supplied for that exact map.

## E. Astronomy placement

The concrete pointer failure was that a preview followed the pointer while the user moved toward the confirmation button. That could change a valid map position into an invalid one just before pressing Place. Clicking the map now holds the attempted anchor until Move Tile is chosen. Invalid attempts remain visible and editable.

Both UI and reducer call the same exploration-attempt validator. It checks tile availability, explicit A/B side, integer rotation, coordinates, overlap, at least four distinct existing contacts, and contact with the selected origin. The actual commit supplies tile ID, selected origin, anchor, rotation and side. No four-contact rule was relaxed.

The real guest scenario uses a physical capital with an interior space, eligible water edge and unrelated map edges. It independently finds fewer-than-four, wrong-origin and valid placements, tries each through the map, then moves the mouse to the real Place button and commits without aborting. The observer gets the committed tile; other-seat projection contains neither the candidate IDs in `cardResolution` nor stack order. The old projection hid the pending choice but leaked the same private candidates through the resolution object.

The previous test clicked Place via DOM `.click()`, skipping mouse travel. The strengthened driver uses continuous mouse movement, waits for moving focus cards to settle and refuses clicks intercepted by another control. This exposed both the placement regression and test-fixture races that coordinate teleporting had hidden. Its camera driver also checks both ends of a drag against the visible canvas; repeatedly starting at a narrow canvas edge had made the test barely pan toward an obscured hex. The fix is confined to the test gesture, not the game's placement rules.

## F. Return order

Buttons now read “Return to Bottom — Next to Be Explored” and “Return to Top — Far End of Stack”. A small labelled stack diagram reinforces the distinction. Numbered thumbnails show future draw order, with a sentence naming the next tile and explaining how many other tiles precede a top return.

Array semantics remain unchanged: normal exploration draws with `pop()`. Four reducer scenarios resolve bottom/top with both order choices and then execute a real `BEGIN_EXPLORATION`; they assert the drawn tile, not just array positions. The multiplayer test additionally follows the return through real turn advancement, a Military card, a deployed army and the Explore button, without resetting the stack.

## G. Dice stability

History comparison: `c05f3c2` added full `renderCombatStage()` calls to the roughly 80 ms visual frame scheduler. Its parent (`9e447cb`, carrying the earlier dice implementation) updated only the die element. Rebuilding the popup on each frame also restarted its entrance animation.

The scheduler again updates only the mounted die. Authoritative combat ID, side, roll sequence and result remain unchanged; cosmetic faces do not call game RNG. Entrance styling applies only when opening the stage. No whole-file revert was used.

The strengthened dice test samples nine animation frames and checks popup/title/player/button node identity, continuous visibility, non-collapsing geometry, changing die faces and the final authoritative face. Existing sequence/reroll/reconnect-baseline checks remain. A separate two-peer test starts a real guest attack and proves an uninvolved observer animates the received roll, lands on the same face and does not replay it on rerender.

The old 14 checks established roll-event behaviour but never asserted popup stability; a rolling class alone could pass while the popup flashed.

## H. Natural Wonder semantics

This was not solely text: raw `terrain` could still activate terrain-type abilities even though the difficulty helper already treated the `wonder` sentinel as 5. `terrainType()` now returns null while a Natural Wonder token is present; terrain-specific consumers in this batch use it. Difficulty remains 5, including Culture and combat consumers.

Hover now identifies the Natural Wonder, no terrain type, difficulty 5, its name and the mapped resource (Mt. Everest/Oil in the browser fixture). It does not print Mountain or Resource: wonder. The original underlying terrain data and existing claim/return model are preserved; this batch does not invent a new post-claim terrain rule.

The actual hover test checks this semantic/display boundary, Culture slots 1–4 versus 5, combat difficulty and unchanged underlying terrain after token removal. The old effect-count gate did not inspect this tooltip.

## I. District-event order

Previously the event queued every player's district effects at once, using `turn.order`, and subsequent order choices could reoffer already resolved kinds. Ordinary ownership checking still allowed a later player to answer their own queued choice early.

`districtEvent` now persists the setup order, cursor, current player and remaining district kinds. It starts at `setup.order[0]` (legacy fallback: turn order), finishes all of that player's nested decisions/rewards, then advances clockwise. Players with no districts are skipped. More than one remaining kind produces an order choice; a sole remaining kind resolves without an unnecessary order prompt. Follow-up choices stay ahead of remaining effects. A response belonging to another seat can temporarily be the head decision without handing it the district event.

Both authorization and the resolver reject a later owner's answer while the current district decision is unresolved. This does not prohibit the current player choosing the order of their own Encampment's effects. The UI shows District Event — Your Turn to the current decision owner and an explicit wait message to everyone else.

The four real peers use P1 with two districts, P2 with one, P3 with none and P4 with two. P1 is deliberately not the host or current turn player. The test checks nested effects, own order choice, waiting displays, P3 skipping and final revision agreement, plus forged host impersonation and an injected future owned choice. Old fixtures expected simultaneous queues and did not test a complete live event.
